# Caps: uses, tries, and what a failure spends

2026-10-29. Trigger: Instagram follow's 15/15 cap was used by 15 failed runs. None clicked Follow (the hint missed a renamed button). Every site shares the rule, so every site had the gap.

## Goal

- A cap counts what the site saw done: a follow, a like, a read that answered.
- A failure that reached the site costs a try. A failure that never reached it costs nothing.
- A few failures leave room to retry. A broken flow still stops the same day.

## Before

`take` reserved the slot before the leg ran. Any failure kept it, except a busy profile. A wrong hint burned the whole day's cap before anyone looked.

## Options

| | How | For | Against |
|---|---|---|---|
| A. Reserve, then settle (chosen) | Reserve before the leg; after it, keep a use, return it to a try, or return both | No overshoot when calls run at once; one place settles | Needs a reach signal from the leg |
| B. Charge at reach | Count only when the leg's first request goes out | Exact | Calls running at once all pass the check, then all count: overshoot |
| C. Fractional charge | A failure costs half a slot | No new counter | Still eats the cap; picks a number with no basis |
| D. Per-platform retry pool | One buffer per site across all actions | Fewer numbers | One broken flow (follow) eats the retries of every other action (like) |

Ranked by: account safety (no overshoot), then a failure must not block good calls, then simplicity. A beats B on safety. A beats C and D on the second rule.

## Rule

- Two counts per `site|account|bucket`: `used` (done, and in flight) ≤ cap. `tried` (all that reached the site) ≤ cap + buffer.
- Buffer: a fraction of the cap, rounded up, at least 1. The default is 0.25 for acts and 0.5 for reads (`RETRY_BUFFER`). Refused acts in a row are a flag of their own, so acts get less. A site or `limits.json` sets `retryBuffer`. A cap of 0 has no buffer.
- Per bucket (action + platform + account), not per platform: see option D.
- Reach (`browser/attempt.ts` `Reach`): a page load (`settle`), an act, any response the run's browser got (an in-page fetch too), or an API request. Offline, a busy profile, or a browser that never started is no reach.
- After the call:
  - ok: a use. If the answer is `already()` (already following), it is a try, not a use.
  - failed and reached: a try. The 502 stays terminal ("failed after spending a try"), so a durable retry does not spend a try per attempt. The caller retries inside the buffer.
  - failed and not reached: nothing is spent. The original error goes up, so Restate may retry it.
- `MeteredCall.spent` marks a failure as reached or not. `site caps` prints tries beside uses and marks unspent failures.
- A caps file from before this reads its `used` counts as `tried`.

## Decision log

- 2026-10-29: chose A, per bucket, with a buffer of 0.25 for acts and 0.5 for reads. William asked for 25–50% on all platforms. Acts take the low end: repeated refused follows can flag an account.
- 2026-10-29: "already" is the explicit `already()` mark, not "no act ran". Some write flows send through an in-page fetch with no `fp.act`. With "no act ran" as the rule, those writes would go uncounted.
- 2026-10-29: today's Instagram follow bucket was moved by hand from 15 uses to 15 tries, because the ledger shows 0 acts on all 15.
- 2026-10-29: an act's proof is the site's own answer, not the button. The button flips before the server answers. TikTok answered `follow_status: 1` and still undid the follow, so TikTok keeps a reload proof. Instagram answers its graphql mutation (`friendship_status.following`, `has_liked`) and sends a block as `errors` or `status: "fail"`: its follow and like read that answer, with no extra load. No answer seen: a reload is the proof. Rejected: a reload on every act (one more page view per act, and it misses a later undo too).
