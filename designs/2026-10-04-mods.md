# Mods

Living doc. Started 2026-10-04. William moved the marketplace and mod system from Parked to now on 10-04, "especially autobrowse". A mod packages what autobrowse learned about a site, so another owner or another install can use it without learning it again. Wren's side, the components catalog, is `wren/designs/2026-10-04-components-and-marketplace.md`.

## What a mod carries

| Kind | Is | Today lives in | Data or code |
|---|---|---|---|
| `walk` | a built walk (`WalkSpec`) | `walks/<site>/<name>.json` | data, run by `walkFlow` |
| `screens` | learned screens for a site (`LearnedScreen`) | `screens.json` | data |
| `fixes` | kept repairs for a flow (`Fix`) | `fixes.json` | data |
| `login` | a site's sign-in as data: `formLogin` or `oauthLogin` inputs (home, origins, fields, provider, before clicks) | `SITE_LOGINS` in `src/auth/sites.ts` | data, new |
| `workflow` | a compiled workflow dir (`index.ts`, test, outline, proof) | `src/workflows/<name>/` | code |
| `site-api` | a site facade's routes | `src/sites/` | code |

Data kinds are read by interpreters that already exist, so installing one cannot run new code. Code kinds can, so they need `--trust`.

## The format

A mod is an npm package with the keyword `autobrowse-mod`, or a local dir with the same layout:

```
mod.json
walks/<site>/<name>.json
screens/<site>.json
fixes/<flow>.json
logins/<site>.json
workflows/<name>/…
```

`mod.json`:

```json
{
  "name": "@someone/autobrowse-mod-calcom",
  "version": "0.1.0",
  "autobrowse": ">=0.3.0",
  "description": "Cal.com: sign in with Google, create an event type.",
  "sites": ["calcom"],
  "domains": ["cal.com", "app.cal.com"],
  "gates": ["send"],
  "credentials": ["calcom:main"],
  "irreversible": false,
  "files": [{ "kind": "walk", "path": "walks/calcom/new-event.json", "sha256": "…" }]
}
```

- `domains`: every origin any file may open. The installer checks each walk's `open` and screen URLs, each login's `origins`, and each fix's `url` against it.
- `gates`: the engine gates the mod's flows can reach (`purchase`, `password`, `send`, `choose`, `human`). A walk marked `irreversible` must list `send` or `purchase`.
- `credentials`: the `site:role` pairs it asks for. It never carries a secret. A walk names secrets by key, and `walkSecrets` resolves them from the installing owner's own stored logins.
- `files[].sha256`: checked on install. npm's own integrity covers the tarball.

## Commands

- `autobrowse mods pack <site> [--walk <name>…] [--screens] [--fixes] [--login] [--out <dir>]` builds a mod from the owner's own state. It scrubs before writing: no secret values, no email addresses or usernames from the owner's accounts, no query strings or fragments on URLs, no cookies. It refuses anything that still matches a stored credential value. It writes `mod.json` with domains, gates and credentials read from the files, and prints what it kept and what it dropped. Publishing is `npm publish`, by hand: it's outward-facing, so it is never automatic.
- `autobrowse mods search [<words>]`: npm registry search on `keywords:autobrowse-mod`. Shows name, version, sites, domains, gates, code or data.
- `autobrowse mods add <npm-name|dir|tarball> [--trust] [--yes]`: fetches, checks hashes and permissions, prints what it will allow, then asks yes (`--yes` skips the ask). Code kinds need `--trust` and must pass `checkCompiled` (tsc + vitest) in place. Files install under the owner's state, `mods/<name>/`. Nothing is merged into the owner's own files.
- `autobrowse mods list` and `autobrowse mods remove <name>`.

## How installed mods load

- **Walks**: `listWalks` also reads `mods/*/walks/`. An installed walk runs as `<site>/walk-<name>`, and the catalog shows its mod. The owner's own walk of the same name wins.
- **Screens and fixes**: read after the owner's own, so learned and kept repairs still win. A fix or screen a mod brought that gets used is copied into the owner's file with `from: <mod>`, so removing the mod doesn't take away what already worked.
- **Logins**: `SITE_LOGINS` gains the data logins, built through `formLogin` and `oauthLogin`. A built-in login for the same site wins.
- **Workflows** (trusted): `loadCompiledWorkflows` also reads `mods/*/workflows/`. They're served by `Compiled` like any other.
- **Guards**: a mod's flows run under the same guards, payment gate, send gate and spend policy as everything else. A mod can never widen `passwordDomains`. A login's origins must sit inside the mod's `domains`.

## The UI

A Mods page in the worker's UI (`:9080`): installed mods with their permissions and what each one's files did (runs that used its walks, fixes used); search results from npm; Add (data mods only, with the same permission screen and a yes); Remove. Code mods install from the CLI only.

## Phases

### M1. Format, pack, add for data kinds

`mod.json` zod schema, `pack` with the scrubber, `add`/`list`/`remove` for walk, screens, fixes; loading from `mods/*`. Tests: the scrubber drops a planted secret, email and query string; a walk opening a domain outside `domains` is refused; a hash mismatch is refused; the owner's walk wins over a mod's.

### M2. Logins as data, search, code kinds

Data logins, `search` on npm, `workflow` with `--trust` and `checkCompiled`. Test: a code mod without `--trust` is refused.

### M3. The UI page and a first published mod

The Mods page. Then pack one real walk from the desk as a sample in `walkthrough/`, scrubbed and checked by hand. It's published to npm only when William says yes.

## Done when

- A walk packed on the desk installs into a fresh owner (`--owner test`), signs in with that owner's own credential, and runs.
- The scrubber test holds, and nothing in a packed mod matches any stored credential value.
- Code never loads without `--trust`.
- Tests pass. The desk restarts cleanly after the deploy (`src/` changes on main restart it within a minute).
