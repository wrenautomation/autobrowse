# Site APIs: a service under its official REST shape, keys made by autobrowse

Status: built 2026-09-21 (facade, LinkedIn + YouTube modules, HTTP + CLI + UI faces,
OAuth). The browser flows behind the gated routes and the setup steps are not
recorded yet (they need the logins: see NEEDS-WILLIAM). Where to attack at the end.

## Decision (William, 2026-09-21)

Usage of a site through autobrowse is the same as the site's own REST API:
`POST /api/sites/linkedin/rest/posts` takes what LinkedIn's Posts API takes
and answers what it answers. Behind one route the official API answers when
a token is in hand; a browser flow answers when the API is gated or absent.
The caller (wren) has one client per site and never picks. autobrowse also
makes the site's keys and tokens itself: developer app, OAuth client, consent.

## Shape

- `src/sites/types.ts` — `SiteApi { site, origin, auth, routes, setup }`.
  `SiteRoute { method, path ("{param}" segments), request (zod, the official
  body/query), api?(input, {token, http}), browser?: Leg & { input?, output? },
  irreversible? }`. A `Leg` is `{ flow: "site/name" }` (hand-written) or
  `{ workflow: "name" }` (compiled: what a recording becomes; run in-process
  with gates approved, its plan = the request, its output = the answer).
  `SetupStep { name, makes, needs?, how: Leg & {input?} | {oauth} }`.
  `OAuthSpec` (authorize/token URLs, scopes, client env names, refresh/access
  token env names, `consent: Leg` that opens `{url}` and clicks through).
- `src/sites/facade.ts` — `siteFacade(sites, {http, env, sink, runner, flow,
  oauthPort})`: `list`, `status(site)` (per route: `via: api|browser|none` +
  `missing`; per setup step: `done`, `blockedOn`, `unrecorded`), `call(site,
  method, path, input)` (path params + query + body → one object → zod →
  leg), `setup(site, step)`.
- `src/sites/oauth.ts` — `accessTokens` (refresh → access, cached; or the
  kept access token), `runConsent` (loopback listener on `OAUTH_PORT` 9400,
  `open({url})` runs the consent leg in the site's logged-in profile,
  code → tokens). Nothing logs a value.
- `src/sites/linkedin.ts` — `/v2/userinfo`, `POST|GET /rest/posts`,
  `/rest/posts/{urn}`, `/rest/socialActions/{urn}[/comments]` GET+POST,
  `POST /rest/images` (initializeUpload). Version header `202508`. Browser
  legs are compiled workflows: `linkedin-whoami`, `-create-post`,
  `-list-posts`, `-post-stats`, `-post-comments`, `-comment`. Setup:
  `developer-app` (workflow `linkedin-developer-app`), `consent` (OAuth via
  `linkedin/oauth-consent`; keeps `LINKEDIN_ACCESS_TOKEN`, 60 days, no
  refresh unless approved).
- `src/sites/youtube.ts` — `POST /upload/youtube/v3/videos` (resumable;
  `file` is a path or URL), `/upload/youtube/v3/thumbnails/set`, `GET
  /youtube/v3/{resource}` with its own query, `POST commentThreads`,
  `POST comments`, `POST /studio/communityPosts` (no official path; hand-written flow
  `google/youtube-community-post`, mapped 2026-09-21 on the channel's Posts
  tab, unproven at the final Post click). Setup: `oauth-client` (workflow
  `google-cloud-oauth-client` on Cloud Console), `consent` (via
  `google-oauth-consent`; keeps `YOUTUBE_REFRESH_TOKEN`).
- Faces: `Backend.sites` (one facade in `backendFor`; what setup keeps is
  visible to the next call at once whichever sink is behind), HTTP
  `/api/sites[/:site[/setup/:step | /*]]` (setup is a job), CLI `autobrowse
  site [status|call|setup]`, UI Sites page (routes, setup runs, a call box).
- Errors keep their status: 404 route/site, 400 request, 501 no leg or flow
  not recorded, 409 setup blocked, the site's own HTTP status on its errors.

## Rules

- A browser leg answers in the official shape (`output` maps the flow's
  result). A route with no official path says so in its summary.
- Publishing routes are `irreversible`; an orchestrator gates them like a buy.
- Legs are looked up live: hand-written flows in `BROWSER_FLOWS`, compiled
  workflows in the catalog (`src/workflows/<name>/`). Recording + compiling
  under the leg's name turns a route from `none` to `browser` with no code
  change; the route's `input`/`output` map the official shape onto the plan
  and the last step's read.
- API first: when both legs exist and a token is present, the API answers.
