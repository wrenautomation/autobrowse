# Reach: research, lead lists, enrichment, outreach

2026-09-25. What autobrowse does for wren beyond its own accounts: read and
search the web, build lead lists, enrich a lead, reach a person. Taken from
two repos William sent: Agent-Reach (MIT) and google-maps-scraper-kit (MIT).

## What we took

| From | Idea | Here |
|---|---|---|
| Agent-Reach | Backends as an ordered list; first that answers wins | `src/reach/web.ts` `firstOf` |
| Agent-Reach | Jina Reader for any page | `read <url>`: jina, then a plain fetch |
| Agent-Reach | Exa search | `search`: exa, brave, then DuckDuckGo's html page |
| Agent-Reach | `doctor` probes, not presence | `site check`, `doctor` |
| Agent-Reach | linkedin-mcp-server (Apache-2.0): a logged-in browser reads LinkedIn | LinkedIn routes on our own browser legs (below) |
| Maps kit | gosom/google-maps-scraper behind a REST API | `maps <search...>` runs it in Docker, writes the CSV |
| Maps kit | CSV straight into the lead store | wren `--format google-maps` (wren 99f5add) |

## What we left

- Agent-Reach's wrappers (twitter-cli, OpenCLI, bili-cli, xiaohongshu, yt-dlp):
  no RIA lives there. yt-dlp returns when content research needs transcripts.
- Cookie-Editor exports: our profiles already hold sessions.
- The Maps kit's scripts: the scraper's own API is enough.
- A Python MCP server for LinkedIn: a second browser stack and a second login.

## Decisions

- **Keys by name, in a header.** EXA_API_KEY, BRAVE_API_KEY, JINA_API_KEY from
  the environment, then the env store. No key: the backend is skipped.
- **A URL with a credential in its query never reaches Jina.**
- **Maps runs on loopback :8090** (Restate owns 8080), `-c 2`, stopped after
  the job unless `--keep`. Docker is the only dependency.
- **LinkedIn reads run as Wren's account** (`linkedin@wren`), never William's
  personal one, at low volume. Connect and message are irreversible and gated.

## LinkedIn

Mapped live 2026-09-25 as linkedin@wren; flows in
`src/browser/flows/linkedin-reach.ts`, routes on the `linkedin` facade under
linkedin.com's own paths.

| Route | Proven |
|---|---|
| `GET /search/results/people` (`keywords`, `page`, `pages`, `network`) | live: 10 a page |
| `GET /in/{vanity}` (`experience=true`) | live |
| `GET /company/{company}/people` (`keywords`, `max`) | live: 30 via Show more |
| `POST /in/{vanity}/connect` (`note` ≤ 200) | dialog mapped, nothing sent |
| `POST /in/{vanity}/message` | unproven: free only to 1st degree; Wren has none |

- **A site with its own logins runs in the chosen account's profile.** The
  facade used to pick a profile only at a provider (Google), so LinkedIn
  browser legs ran in `linkedin`, William's personal account. Now the
  policy's account resolves to `linkedin@wren`, and no matching profile is a
  409, never a fall back to his.
- **"Allow pages to see that you visited" is answered "Don't allow".** The
  modal covers every page until answered; clicks under it time out.
- **Free-tier limits:** five notes a month, a monthly search cap (the flow
  hands over when LinkedIn says so), messages only to connections.

## Where to attack

1. DuckDuckGo's html page can serve a bot check; search then fails unless Exa
   or Brave has a key. Brave's free tier is the cheap fix.
2. `site status` says "token ok" for a token site whose bare token belongs to
   its own login while the call runs as the policy's account (npm, Langfuse):
   the listing is optimistic, the call is right.
3. `message` has never run: the compose box selector is LinkedIn's aria
   pattern, not a mapping. Prove it on the first 1st-degree connection.
4. LinkedIn's classes are build hashes; the flows find things by role, text
   and `/in/` links. A redesign breaks them loudly (empty rows), not silently.
