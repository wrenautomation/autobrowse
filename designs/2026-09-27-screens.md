# Screens: determinism over a shifting UI

2026-09-27. Status: built (walker, interrupts, learned screens, model
reader, Cloudflare sign-in as a walk, `screens`, `login --all`). Other
sign-ins convert as they break.

## Ask

William: Cloudflare's login changed under a flow ("Sign in as jinwi…"
because the browser remembered the account). Workflows need multi-layer
fallbacks so one changed page does not mean healing and cycling through
brittle scripts. Can failures be preempted? Can conditionals detect the
page and run the right deterministic code? Are model steps unavoidable?
Is determinism a realistic goal at all?

## Answer

Strict determinism over a UI we do not own is not achievable: code that
has never seen a variant cannot handle it on first sight. What is
achievable, and what this builds: **determinism for every state seen
once.** Every known screen has one plain-code response. Nondeterminism is
confined to first sight, where a model only picks from a closed list (or
names one non-committing click), the pick is verified by the page moving
on, and it is kept as data. The frontier shrinks per site; committing
actions never touch it.

The root cause is not moved buttons, it is *wrong page*: sites branch on
state (remembered account, first visit, new device, A/B). A linear script
assumes one path, and each variant becomes a one-off `if` in one flow,
found mid-task, fixed by a model each time.

## Shape

A **screen** = recognizer + handler, both plain:

```ts
{ name: "saved profile",
  looks: "'Continue as <email> using Google', with 'Sign in with another profile'",
  shows: [SAVED_PROFILE],                 // at?: URL, hides?, says?, is?
  act: async ({ fp }) => …               // one handler
}
```

Two consumers:

- **Walks** (`walk(ctx, w)`) for flows whose path branches: a site name,
  a goal, screens in order (goal first, forms last). Look → first match →
  act → wait until that screen is gone → look again. Popups: a handler
  switches to one; a popup that closed itself hands the walk back to the
  opener. The same screen three times running is stuck; 12 steps is the
  cap. Cloudflare's sign-in is the first: dashboard, google, saved
  profile (ours → ride the live Google session, nothing typed; someone
  else's → "Sign in with another profile"), rejected (previous password
  once), code, login form (password, or the Google button for a `via`
  account).
- **Interrupts** for every other flow, unchanged. Before an act, the
  runner waits for the control while looking for what may be in its way;
  an overlay (cookie banner) is looked for once per page even when the
  control shows. A late overlay (the click failed) is handled once and the
  op retried. Interrupt clicks are not the flow's acts: they do not shift
  the count that keys irreversible acts.

**Learned screens** (`~/.config/autobrowse/screens.json`, `SCREENS_FILE`):
a page by URL shape (ids → `*`) plus up to 8 landmarks (headings, buttons,
fields; addresses and numbers blurred), and what worked: a walk's screen
by name, or one click. Kept **per site**, so a repair's detour in one flow
is an interrupt for every flow on the site from then on. A row that stops
working is dropped. Fewer than 2 landmarks is too bare to keep.

**The ladder** for a page no screen knows, cheapest first:

1. coded screens (ms)
2. learned screens (ms, data)
3. the model (`llmScreenReader`): given the goal, the walk's screens by
   name and look, the URL and the interactive elements, it answers with a
   name from the list or one click. Anything else is refused; a click that
   buys, pays, sends, submits, deletes or confirms is refused. It never
   acts. Its answer is kept only after the page moved on.
4. the walk fails: `LoginFailed` for a sign-in (the next stored method
   tries), else a person, with the usual artifacts.

## Preempting

- APIs over UI wherever one exists (Cloudflare mints tokens by API from a
  bootstrap token; the sign-in walk is for when a dashboard is the only
  door).
- `autobrowse login --all`: every stored account, one after another.
  Run daily: sessions stay warm, and a changed page is met and learned on
  a quiet run, not mid-task. Exit code 1 when any failed.
- Persistent profiles (already): a remembered account is a saved profile
  screen, not a surprise.

## Rejected

- Model steps inside flows: slow, nondeterministic, and they hide drift
  instead of surfacing it. The reader is the smallest use that still
  avoids "stuck": pick, never act, then compile to data.
- Playwright's `addLocatorHandler`: fires whenever its locator is
  visible, before any action, anywhere on the page. Right for a cookie
  banner, wrong for a learned click (a "Continue" that is the flow's own).
  The runner's own check runs only while the control is missing.
- A per-flow store for detours (the old `fixes.detours` stays for
  `repairs --apply`, which writes them into compiled source); the shared
  copy is the site-wide interrupt.

## Where to attack

1. Google's own sign-in (`signInToGoogle`, 160 lines of `if`) is the
   walk that would pay most: every "Sign in with Google" goes through it.
   Convert it screen by screen the next time it breaks.
2. Coded interrupts are one (cookie banner). "Not now" passkey nags,
   "Stay signed in?" and the like are site-worded; they arrive as learned
   clicks first. Promote the ones that repeat.
3. Landmark matching is a subset test on ≤8 names. A page that renames
   its heading drops the row (fine) and one that keeps the names but
   changes meaning would still match (a click, non-committing, then the
   step fails the usual way). Watch `screens` for rows used often on
   several URLs.
4. `login --all` is a command, not a schedule. Put it on the box's clock
   once the token-renewal loop has a slot beside it.
5. A learned `screen` row names a screen of one walk; a walk renamed loses
   it. Rows are cheap; forget and relearn.
