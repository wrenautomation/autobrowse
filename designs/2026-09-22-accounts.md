# Accounts the agent makes

Wren needs accounts (Instagram, YouTube, Facebook Page, X) and the box
needs the credentials the laptop has. Both are code paths, not hand work
(see memory: everything automated incl. auth).

## Credentials on every machine

- Laptop store: `~/.config/autobrowse/credentials.json`, sealed. Box: env,
  `AUTOBROWSE_CRED_<SITE>_*` from SSM `/autobrowse/config`.
- `creds push <site>` (2026-09-22): `credentialEnv(site, cred)` → USERNAME,
  PASSWORD, TOTP_SECRET, VIA, CODES_INBOX → `envStore.put` each. Nothing
  printed. `envCredentials` now reads via-only credentials (no password)
  and CODES_INBOX. Recovery codes and passkeys stay on the laptop.
- `creds push [sites...] --all` / `creds pull [sites...] --overwrite`
  (2026-09-22): `pushCredentials` / `pullCredentials` in `credentials.ts`.
  Push skips canaries (a tripwire belongs to one machine). Pull keeps a
  site already here unless `--overwrite`, and keeps local passkeys and
  recovery codes either way. Env names carry the account mark:
  `google@ops` → `AUTOBROWSE_CRED_GOOGLE__OPS_*` (double underscore), so
  `list` reads it back as `google@ops`.

## Signup

- `place {hints, secret}` on the explore socket: fills a field with a
  value the session holds by name (`ExploreOptions.secrets: (name) =>
  value | null`). The journal keeps an `input` with `redacted: true`, so
  the compiled flow reads it as `{from:"secret", key}`. The agent has
  `place{ref,secret}` and a `SECRETS (use place): …` line; values never
  enter a prompt.
- `signupSecrets({cred, codes, since, phone})`: `email` (the codes inbox),
  `username`, `password`, `phone` (paired phone → Linq → Twilio), `code`
  (email then SMS through the sign-in code sources; `since` advances after
  each code so a resend is a new code).
- `mintCredential(store, {site, email})`: `newPassword()` (24 chars, or
  the site's cap in `PASSWORD_MAX`: TikTok 20), stored sealed as
  `{username: email, password, codesInbox: email}` BEFORE the browser
  opens; refuses when `site` already has a credential. The same address
  again is the stalled attempt: its password stands, unless it breaks the
  site's cap and the account was never made (no `madeAt`): then it is
  replaced (2026-09-23, TikTok's Next stayed disabled on 24 chars).
- `explore <site> --signup <address> --codes <inbox>` (2026-09-23): the
  signup driven by hand over the socket, same secrets as the agent's. The
  way through when the agent fumbles a form (TikTok's year picker). A
  signup session never signs through a wall with a stored credential
  (`signIn: false`): the signup page is the point.
- Signup by provider: `creds via <site> google --for default --url
  <signup page>`, then `login <site>` runs the Google round trip; the
  site's own onboarding (birthday, handle, a password via `explore
  --new-password`) follows in explore.
- App-only walls (2026-09-23). The browser passes every rebrowser
  bot-detector test (no runtime/webdriver/init-script leaks), so what
  stops these is the site's risk check, not our fingerprint:
  - TikTok: email + code + password → `/login/download-app`, no account.
  - X: email signup is "only allowed on the apps". Google round trip +
    birthday + @wrenautomation (free) + password → "Sorry, please try a
    different method". Phone (Canada +1) keeps Continue disabled.
  - Way through: the apps. A phone leg over iPhone Mirroring (Vision OCR
    finds text on the mirrored screen, a click lands on it, same
    target-by-name model) needs Screen Recording + Accessibility granted
    once to the terminal. Until then William signs up in the app, then
    `creds made`, and web sign-in takes over.
- X clicks: the onboarding dialog's buttons time out on a pointer click
  (something covers them); `press Enter` on the control works.
- `autobrowse signup <site> --email --name --handle --birthday --url
  --headed`: mint, then the agent with `signupGoal` (names the secrets and
  the details, never a value) and the secrets; `human` → headed: press
  enter after the captcha; headless: the run ends. Recording
  `signup-<site>` → compile for the next time.

## Any inbox, not only ours (2026-09-22, William's reframe)

A code inbox outside our Workspace is not a dead end: autobrowse sets up
its own access. `gmail` site (`src/sites/gmail.ts`), one consent per
account: `accountEnv(name, account)` names the token
(`GMAIL_REFRESH_TOKEN__WILL_X_DEV`); `accessTokens(spec, account)`;
`facade.setup(site, step, account)` runs the consent flow under the
`<site>@<label>` profile whose credential has that username
(`profileOf`), and `OAuthSpec.identity` (GET profile → address) keeps a
plain consent under the consenting address too. `googleTokens` acts as a
consented address through that token before falling back to the service
account. Proven live: jinwilliam.jin@gmail.com consented, Gmail API
enabled by the agent, inbox read by the code source.

## Which account for what (2026-09-22, William: "per account must be first class")

William runs several Google accounts with a rule: `jinwilliam.jin@gmail.com`
for anything that pays, `william@wrenautomation.com` (or `will@williamjin.dev`)
for everything else. That rule is data, not something each command guesses:

- `src/auth/identities.ts`: an *identity* is `{address, at: google|microsoft,
  for: [purposes]}`; `identityFor(all, purpose)` answers the account that
  names the purpose, else the `default` one; `identityAt` narrows to a
  provider. Purposes are open words; `pays`, `default`, `signup` are the ones
  the code asks for. File `~/.config/autobrowse/accounts.json`; the box reads
  `AUTOBROWSE_ACCOUNTS` (`a@x=pays;b@y=default,signup;c@z@microsoft=…`).
- `autobrowse accounts [list|add|use|remove|push]`: the policy and each
  account's readiness (credential found by username across `google`,
  `google@…`, `google-…`; inbox readable: consented or in the Workspace
  domain `GOOGLE_WORKSPACE_DOMAIN`; tokens kept under its name). Names only.
- Where it is read: `SiteApi.purpose` / `SetupStep.purpose` (meta = `pays`);
  the facade's `accountFor(site, step)` (`accountForSite` in `wire.ts`) picks
  the account for a call or consent that names none, only for sites whose
  consent signs in at an identity provider (`google/…`, `microsoft/…`). A
  policy pick still falls back to the site's own token on a call, and a
  consent it ran keeps the token under the site's own name as well as the
  account's, so what worked before the policy keeps working. `signup` takes
  `--for <purpose>` (default `signup`) and refuses early when that inbox is
  not readable; `creds via --for pays` picks the provider account by purpose.
- Seeded 2026-09-22: jin = pays; william@wrenautomation.com = default,
  signup; will@williamjin.dev = personal. Only jin's inbox is readable:
  william@'s consent hits Google's passkey challenge (`challenge/pk/error`,
  the virtual authenticator is not the passkey Google wants), will@'s needs
  its credential. Until one of those clears, `signup` needs `--email
  jinwilliam.jin@gmail.com` (or `--for pays`).

## Decisions

- One `place` command, not a `fill {secret}` variant: the schema stays
  one field per meaning and the journal branch is one line.
- Codes by the same sources as sign-in (`codesFor` extracted from
  `loginFor`): one place knows the inboxes.
- Password minted before the run, never after: a stall mid-form still
  leaves a usable credential; the model never sees it.
- No captcha solving: a hand-off in a headed window.
