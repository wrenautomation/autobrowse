# Papers

2026-10-12. William: "For government ids for verification can we have a tunnel or encrypted
token for accessing secure bucket photos for driver licence? And have credvault / autobrowse
support that?"

Meta Business Verification, a registrar, a bank: some forms want an ID photo. Papers keep them
and put them on a page under the same rules as a card.

## Where they live

- **The Mac:** `~/.config/autobrowse/papers/`, one sealed file per paper plus a sealed index,
  under the wallet's Keychain key (AES-GCM, 0600, 0700 dir). Mac only, default owner only.
- **The backup:** S3 `autobrowse-prod-papers-<account>` (`deploy/terraform/papers.tf`). SSE-S3,
  versioned (old versions expire after 90 days), public access blocked, TLS only. Its policy
  denies `s3:*` to every principal but William's IAM user, so no machine role, Lambda, box or
  owner role reads it whatever its own policy says. `PAPERS_BUCKET` names it; unset, no backup.

## Getting one in

- `autobrowse papers add <name> <file> --kind drivers-licence --side front`. The type is read
  from the bytes (JPEG, PNG, HEIC, WebP, PDF; 12 MB at most). `--remove-original` deletes the
  file once stored.
- From a phone, a drop: `autobrowse papers ask <name> --kind … --side …` prints
  `https://phone.wrenautomation.com/u/<id>#<key>` and waits. The page asks for Wren's operator
  sign-in (`--open`: none, for someone outside Wren), seals the photo in the phone's browser
  under the fragment's key (WebCrypto AES-GCM) and posts only ciphertext to the phone Worker's
  KV, once. The Mac takes it once (HMAC signed with `CRED_LINK_SECRET`), opens it, seals it and
  backs it up. The key never leaves the link; the Worker never sees the image.

This is the "encrypted token": a credential link (wren `designs/2026-10-06-credential-links.md`)
the other way. No tunnel: the desk that uploads is this Mac, so the paper never travels to
reach it. The box can't upload papers.

## Putting one on a page

`upload{files:["paper:<name>"]}` in explore. The first upload of a paper on a host asks a
person (the approver, as a card does); the yes lasts the session. Every attempt is audited
(`credential: paper:<name>`). The bytes go to Playwright from memory; no plaintext file is
written. Papers and paths go in separate uploads.

## Decision log

- Kept in autobrowse, not credvault: credvault holds generic secret primitives (sealing,
  stores, audit, SSM sync) and no browser. A paper, like a card, is policy about when a
  person's document may land on a page. It uses credvault's `Cipher`.
- The bucket copy is plaintext under SSE-S3, like the wallet's SSM backup under KMS: a dead
  Mac loses its Keychain key, and the backup must restore on a new one. The bucket policy is
  what keeps it William's. No KMS key: a new key costs monthly and adds nothing over the deny.
- In-memory upload, not a temp file: Chrome reads an `<input type=file>` path lazily, so a
  temp file deleted after `setInputFiles` uploads as 0 bytes.
- `papers ask` polls the Worker every 3 s while it waits: one signed POST, only while a person
  is about to send. A push isn't worth it for a one-off.
